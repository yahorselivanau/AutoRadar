# AGENTS.md

Этот файл обязателен для Codex и любого coding agent, работающего с репозиторием.

## 0. Приоритет инструкций

При выполнении задачи агент применяет инструкции в следующем порядке:

1. текущие прямые инструкции владельца проекта в чате;
2. правила из `AGENTS.md`;
3. требования и решения из остальных файлов проекта.

Если текущая инструкция владельца проекта противоречит `AGENTS.md`, `PRD.md`,
`ARCHITECTURE.md` или другому файлу репозитория, агент следует текущей
инструкции владельца и при необходимости обновляет устаревшие документы.

## 1. Цель

Создать рабочий mobile-first MVP AI-агрегатора автозапчастей для Беларуси.

Главный приоритет:

> Стабильно получить и показать реальные предложения из нескольких источников.

Не тратить время на преждевременную инфраструктуру, сложный кеш или абстракции без работающих адаптеров.

## 2. Источник истины

Перед изменением кода прочитать:

1. `README.md`
2. `PRD.md`
3. `ARCHITECTURE.md`
4. `SOURCE_ADAPTERS.md`
5. `DESIGN_SYSTEM.md`

При конфликте:

- продуктовые требования: `PRD.md`;
- технические решения: `ARCHITECTURE.md`;
- правила агента: `AGENTS.md`.

## 3. Технологические правила

- TypeScript strict.
- pnpm.
- Turborepo.
- Next.js App Router.
- Server Components по умолчанию.
- Client Components только при необходимости.
- Zod на всех внешних границах.
- Денежные значения хранить как decimal/numeric, не float.
- Все даты в UTC.
- UI отображает BYN.
- Не хранить секреты в коде.
- Не отправлять `SUPABASE_SECRET_KEY` клиенту.

## 4. Порядок работы над источником

Для каждого сайта создать исследовательский отчёт:

`actors/search/src/adapters/<source>/DISCOVERY.md`

Он должен содержать:

- публичный URL поиска;
- поддерживаемые типы поиска;
- проверку robots/условий;
- нужен ли логин;
- какой способ выбран;
- обнаруженные параметры URL/form;
- обнаруженные публичные XHR/fetch endpoints;
- обязательные headers/cookies;
- селекторы;
- пример запроса;
- известные ограничения;
- нужна ли source-specific proxy-конфигурация;
- требования к TLS и доверенному CA;
- дата проверки;
- причина выбора HTTP/HTML/JSON/Playwright.

### Обязательная лестница

1. HTTP + URL parameters.
2. Server-rendered HTML + Cheerio.
3. Публичный JSON/XHR обычным HTTP.
4. Playwright.

Запрещено начинать с Playwright, пока не доказано, что первые три варианта не подходят.

## 5. Не выдумывать интерфейсы сайта

Нельзя:

- придумывать endpoint;
- угадывать названия form fields;
- использовать селекторы без проверки;
- считать поисковую страницу API;
- утверждать поддержку VIN без теста.

Каждый вывод должен быть подтверждён:

- реальным запросом;
- сохранённой fixture;
- тестом;
- записью в `DISCOVERY.md`.

## 6. Контракт адаптера

Все источники реализуют общий интерфейс из `packages/domain`.

Адаптер обязан:

- возвращать только нормализованные предложения;
- сохранять исходную ссылку;
- иметь timeout;
- возвращать typed error;
- корректно обрабатывать пустую выдачу;
- не ломать общее задание;
- сообщать способ получения данных;
- иметь health check или smoke test.

## 7. Классификация данных

Нельзя угадывать:

- original/analog;
- new/used;
- наличие;
- совместимость.

При недостатке информации ставить `unknown`.

AI не исправляет результат адаптера скрыто. Все преобразования должны быть воспроизводимым кодом.

## 8. План реализации

### Фаза A — фундамент

- создать monorepo;
- настроить Next.js, Supabase и Apify;
- добавить migrations;
- добавить auth/guest session;
- создать типы домена;
- создать mock adapter;
- реализовать search job lifecycle;
- сделать прогресс и выдачу на mock data.

### Фаза B — реальные адаптеры

Порядок:

1. Remzona.
2. Один наиболее простой дополнительный источник новых деталей.
3. Второй источник новых деталей.
4. ARMTEK.
5. AV-parts в зависимости от технической доступности.
6. Дополнительные источники после стабильности первых.

Порядок может измениться только после `DISCOVERY.md`.

### Фаза C — AI

- structured extraction;
- active vehicle;
- clarification buttons;
- tool calling;
- запуск поиска;
- отображение результатов в чате.

### Фаза D — гараж и VIN

### Фаза E — mobile UX и QA

- E2E tests.

## 11. Definition of Done для адаптера

Адаптер готов, когда:

- есть `DISCOVERY.md`;
- есть fixture успешной выдачи;
- есть fixture пустой выдачи;
- unit tests проходят;
- smoke test может быть запущен вручную;
- возвращается минимум title, source URL и состояние;
- цена парсится корректно, если видна;
- OEM парсится только если присутствует;
- результат отображается в общей выдаче;
- timeout/ошибка не ломает другие источники;
- feature flag позволяет отключить источник.

## 12. Definition of Done для пользовательской функции

Функция готова, когда:

- работает на mobile и desktop;
- имеет loading, empty и error состояния;
- покрыта типами;
- имеет хотя бы один тест;
- не требует регистрации без продуктовой причины;
- не раскрывает секреты;
- не теряет состояние при открытии выдачи.

## 13. Тестовые запросы

Создать набор из минимум десяти сценариев:

- точный OEM с дефисами;
- тот же OEM без дефисов;
- деталь с левой/правой стороной;
- деталь с передней/задней позицией;
- популярный европейский автомобиль;
- редкий запрос;
- VIN с успешным best-effort decode;
- VIN без достаточного decode;
- отсутствие результатов;
- один источник timeout.

Не использовать реальные персональные VIN в репозитории.

## 14. Работа с AI

- prompts хранятся версионированно;
- structured schema находится в коде;
- model name задаётся env;
- provider меняется через фабрику;
- tool execution выполняется сервером;
- результат модели валидируется;
- при ошибке schema показать ручную форму;
- модель не получает service credentials;
- интернет-инструмент модели выключен для поиска применяемости.

## 15. Работа с базой

- только migrations;
- типы БД генерируются;
- RLS тестируется;
- service-role используется только сервером/Actor;
- запросы должны быть индексированы по `user_id`, `search_job_id`, `source_id`;
- сырые HTML-страницы в PostgreSQL не хранить;
- диагностический raw payload хранить только в dev или как hash.

## 16. Коммиты и отчётность

После каждой завершённой задачи обновлять:

- код;
- тесты;
- соответствующий документ;
- `CHANGELOG.md`.

В ответе владельцу проекта указывать:

- что реализовано;
- какие команды запускались;
- какие тесты прошли;
- что не удалось проверить;
- какие источники заблокированы или требуют разрешения.

Нельзя заявлять, что адаптер работает, если он проверен только по предположению или устаревшей fixture.
